# 当前场景人物模型替换调查

状态：MVP 实机更新后人物不可见，应用与恢复入口已紧急停用。当前人物身体、脸和头发的只读显示仍可使用。

## 2026-11-15 实机故障

Live 场景对实例 `-55402`、索引 `0` 应用身体 `mdl_chr_hski-cstm-0002_body` 后，游戏返回成功对象，但既有的实例或管理器索引校验失败；用户报告人物消失。日志未分别记录返回实例及索引，不足以判断究竟哪个检查失败或对象为何不可见。自动恢复因身份不匹配未执行；之后对实例 `-58786` 的另一次应用请求未出现 BEGIN，不能据此认定它被更新。不得假设后一个实例必然是原角色的替代对象。安全修复阻止后续应用及恢复，不修改已经运行的游戏进程。

## 已知事实

- 场景扫描能找到已激活的 `CampusActorController`，按准入场景过滤；人物描述提供 `get_body`、`get_face`、`get_hair`。历史只读诊断记录过两个现有人物的资源和部件。
- 游戏元数据记录 `CampusActorManager.UpdateActorAsync(Int32, CampusActorDescriptor, CancellationToken)`，返回 `UniTask<ValueTuple<Boolean, ICampusActorController>>`。签名并不说明它会不会复用、替换或销毁现有人物，也不说明失败后的状态。
- 已有 `CreateActor` + `BuildAsync` 路径针对插件创建的新实例；它的归属、回滚与基线检查不能直接用于游戏人物。早期共享缓存更新事故导致人物消失，详见 VALIDATION.md。
- 三参数 `CreateActorDescriptor` 可以创建身体、脸、头发组合，但不能据此假设新描述包含原人物的全部设置、道具、身份和其他属性。仅保存三个字符串不构成可靠恢复。
- 对本机 `global-metadata.dat` 的只读索引显示，`CampusActorDescriptor` 有身份、自动眨眼、ADV 设置、身高校正及关节限制；其 VL 描述类型还声明模型资产、游戏对象、道具索引和约束等字段或访问器。该索引只证明成员名称，不证明继承、字段类型、拷贝语义或更新行为。
- 拍摄场景的只读实机诊断确认了上述类型层级及字段类型；`get_assets()` 实际返回 `List<String>`，不是此前诊断假定的字符串数组。后续实机诊断对三个现有人物均成功创建独立描述副本和资源列表，并验证副本和原描述的身体、脸和头发保持一致；三个样本的资源列表分别只有身体、脸、头发三个条目。这只验证同值复制，尚未验证跨人物资源替换，也没有调用游戏更新接口。浅拷贝仍共享描述中的其他引用字段，因此不证明更新或恢复安全。
- 安装只读诊断版前的 DLL 与 `build/scene-actors-head-preview/GakuActors.dll` 的 SHA-256 一致，原 DLL 与配套窗口已备份。任何后续安装前都要退出游戏并核对版本及哈希。
- 元数据还显示 `SafeUpdateActorAsync` 的异步状态机持有 `ActorInfo`、索引、描述及取消令牌；`ActorInfo` 含描述、索引、生成状态和成功状态。这些成员名表明该流程与管理器状态有关，但不揭示状态何时更新、失败时是否保留原对象或与缓存如何关联。
- 本机 `Player.log` 中有 `MotionDefinePlayerTimelineTrackLayerBehaviour.ProcessFrame` 访问空组件的异常，部分堆栈经过 Live Seek。日志没有会话标识、人物 ID 或可与模型更新精确关联的时间，不能确认与事故是否处于同一会话，也不能证明它由本次操作引起；该日志已另存为 `actor-model-emergency-lock/incident-player-log.txt`。
- 先前的只读 Live 代码采集显示 `LivePlayerPresenter` 自身保存 `_actors` 并暴露 `get_Actors`，`Live3DPresenter` 另有 `_actors`、`_binder`、`SetActorsAsync` 和 `SetupLiveBinderAsync`，`CampusLiveBinder` 也有 Actors / VirtualActors 和 BindActor。这些是成员与签名证据，尚未证明哪些对象在本次事故后仍指向旧实例，也不能把这些接口作为已验证的重绑定方法。
- 元数据还显示，`MotionDefinePlayerTimelineTrackLayerBehaviour` 自身有 `_player` 和 `_controllers` 字段，其 `Create` 接收 `player`、`controllers`；这增加了对 Timeline 内引用的调查必要性，但字段名不能证明其类型、当前值或与事故的因果关系。
- 本次源码增加了显式读取目录时的只读日志：逐一对照同场景人物和管理器按索引返回的实例；在唯一确认 Live 场景管理对象后，读取播放器、3D 场景及绑定器的人物容器，尝试记录元组中的人物引用，并记录相关接口的元数据。它不会调用更新、绑定或销毁方法；尚未安装或进行新的游戏内验证。安全锁保持开启。

## 需要的证据

1. 对实际人物的描述类型做元数据检查，确认完整字段、属性及可行的独立副本构造方式。读取人物目录时的现有诊断现会输出描述字段和访问器签名，不调用新增访问器。
2. 在可隔离的测试场景验证 `UpdateActorAsync` 的索引、描述、控制器实例和管理器映射的生命周期；核对成功、失败、取消及场景切换后的对象和其他人物。
3. 验证保存完整原描述后恢复，包括道具、物理、动画绑定、可见性及姿态；失败时不能假设再次调用一定能恢复。
4. 加入目标身份和场景代次校验、单任务串行、资源就绪检测，明确与动作插件及资源显隐状态的协调，再实现界面和命令。

不要把单独复制 `body/face/hair` 或对现有对象调用 `BuildAsync` 视为已验证的恢复方案。任何游戏内结果须分别记录游戏版本和复现步骤。

## 入场前选择方案（2026-11-15）

- 对当前游戏的只读元数据索引显示，图鉴 Live 确认页有 `PictureBookLivePlayConfirmSheetModel.Costumes`、人物服装按钮、`UpdateCostumes`；服装选择页有 `OnClickBody`、`OnClickHead`。选择页面与当前人物编辑系统的具体对象关系及调用顺序仍需实机验证。
- `LiveFixedData` 有 `Descriptors` 和接收 `costumes` 或 `descriptors` 的构造函数；`LivePlayerPresenter` 有 `CreateDescriptors`、`PreloadAssetsAsync`、`LoadCharacterAsync`、`Initialize3DActorsAsync`、`CreateActorAsync`；`Live3DPresenter` 有 `SetActorsAsync`、`SetupLiveBinderAsync`。这些签名说明存在入场前描述和后续加载、绑定的可研究路径，但不证明某个 getter / 构造函数是所有 Live 共用入口，也不证明已知调用顺序。
- 优先研究让游戏在**预加载前**收到完整、独立的角色描述，让原生流程构建并绑定，避免对已经用于演出的 controller 调用 `UpdateActorAsync`。先区分游戏提供的服装／头部组合和 GakuActors 的身体／脸／头发自由组合；后者可能没有对应的 `Costume`／`CostumeHead`，不能假设确认页直接接受它。
- 资源管理器当前仅对拍摄 / Live 进行场景准入，歌曲选择 / 确认页不在门控内。需要先实现严格的确认页面识别和只读诊断，再确定描述的拥有者、传递时机、所需预加载和返回原组合的生命周期；不要放宽对整个主页的扫描。
- 入场前应用只影响后续构建，不会自动实现正在播放中的无缝切换。作为后续研究可评估停止、重建演出并跳转回时间点，但音频、镜头、Timeline、动态物理、道具和人物绑定需要分别验证；不能把这个过程称为已经验证的无缝切换。
- 本方案尚未实现或实机验证，不关闭现有应用 / 恢复安全锁，不写入玩家默认服装、预设或游戏数据库。
- 代码正在增加独立的入场前只读诊断窗口：窗口打开时尝试唯一确认图鉴 Live 服装选择界面及其页面模型，并按识别的人物查看现有自定义预设；可手动刷新并输出更详细的元数据。它不会写入数据、应用预设或影响 Live；检测到页面与读取到人物、服装字段是两个独立结果，均需真实页面验证。演出中替换入口从界面和桌面协议移除，底层安全锁保留。
- 实机截图和日志确认可识别 `PictureBookLiveCostumeSelectSheetPresenter`，并读到身体 `hski-cstm-0000` 与头部 `costume_head_hski-cstm-0000` 等记录；人物标识为空的一个明确代码原因是字段读取器漏掉 IL2CPP 字符串类型，已在源码修复，尚待再次实机验证。新增手动选择人物分类，读取人物目录前需确认服装页当前仍存在；可用已存预设中的分类作为回退。
- 用户反馈确认后再次进入才看到期望服装。现有日志显示选择页面保持可识别的一段期间读到多个不同头部 ID，但日志没有用户点击 / 确认事件时间，不能判断变化发生在确认前还是确认后。源码加快窗口内只读观察并在读取耗时较高时降低频率，明确显示“选择页读取值”与游戏确认状态可能不同；补充只读输出确认页服装集合的类型与结构，等待实机采样。不能把轮询频率调整宣称为已解决游戏服装提交时序。
- 后续源码以现场播放确认页为识别入口，尝试读取该页模型中的已确认服装集合，并支持手动选人物、按人物分类选择身体／脸／头发、载入已有预设到编辑器。确认页集合的实际运行时结构尚未验证，不支持的结构会明确报告而不猜测；预加载前写入的接口和生命周期仍未证实，编辑器尚不能应用至 Live。这些改动尚未实机验证或安装。
- 离线反汇编了历史采集的 `LivePlayerPresenter.CreateDescriptors`、人物加载及预加载状态机，结果保存在工作区 `prelive-offline-analysis`。`CreateDescriptors` 从 `LiveModelHelper` 指向的对象链读取一个集合并返回枚举管线；`<CreateDescriptors>b__31_0` 捕获片段对描述参数偏移 `0x58` 写入 `1`。这说明不能假定描述在生成流程中只读；字段的真实含义、预加载参数与该对象链的实例是否相同、两个缓存生成顺序和真实集合的元素类型仍未得到证明。历史捕获包含截断片段，不能据此推断完整控制流或写入接口。
- 新源码在识别到唯一确认页时自动记录该页集合及 Live 固定数据、辅助对象和预加载接口的类型信息，并自动尝试一次人物／服装目录读取；人物自动识别只在确认页的身体和头部 ID 均在目录中且归属一致时采用，可手动覆盖。这些是本地准备，仍不代表已验证确认页读取或预加载替换。
- 2026-11-15 实机日志验证：确认页实际有 1 个 `ValueTuple<Costume, CostumeHead>`，读取到身体 `hski-cstm-0000`、头部 `costume_head_hski-cstm-0000`；人物及服装目录读取到 25 / 580 / 427 项。`LiveFixedData.Descriptors` 的声明类型是 `List<CampusActorDescriptor>`，原始及附加描述缓存是只读列表；预加载签名的四个参数分别为 `LiveFixedData`、`LiveModelHelper`、进度回调和取消令牌，返回 `UniTask`。这些类型已确认，但对象一致性、缓存生成时序和成功构建仍未验证；该版没有写入或替换入口，因此用户反馈未切换是预期结果，不是游戏接口返回失败。
- 之后增加单人 Live 预加载实验路径：在确认页登记一次目标，在预加载入口检查捕获的 Windows x64 函数前缀、签名、值类型尺寸、人物、原服装、固定数据对象一致性和两个缓存尚未生成；复制描述及资源列表并替换单个条目，监视任务状态与 Live 人物实际部件。前置检查失败时使用原流程；任务失败且缓存仍为空时尝试恢复原描述，否则提示重新进入 Live。目录或资源索引不证明模型已下载，只有实机人物部件、骨骼及渲染等回读能提供构建证据；任务状态监控与恢复、实际资源可用性均尚待实机验证。2026-11-15 已备份并安装本地编译的插件及配套桌面窗口，原文件位于 `prelive-apply/backup-20261115-2209`。
- 2026-11-15 后续测试：日志只出现 `ARMED`，未出现提交或拒绝，Live 仍回读原人物。历史捕获的实际调用点将尾部 `MethodInfo` 参数置零，旧钩子却要求与非空方法指针严格相等，导致静默跳过；已改为接受空指针或完全匹配，并记录命中、线程、跳过及进入场景仍未命中的情况。此前确认页只读取主表并未启动 Octo 模型索引；历史索引中已存在用户选择的 `hkne` 身体、脸和头发，现已支持确认页分帧启动索引，但索引并不证明资源已下载。两项修正仍需实机验证。
